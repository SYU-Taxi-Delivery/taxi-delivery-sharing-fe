# 로그인·회원가입·인증 상태 (#5)

> 학교 이메일 인증번호로 회원가입·비밀번호 재설정을 진행한다. 로그인 사용자 정보는 로그인 응답을 기억하고 보호 API의 401로 만료를 처리한다. [백엔드 연동 안내](../../../docs/backend-integration.md)

첫 화면(`/`)은 같은 로그인 화면을 제공한다. 로그인 성공 또는 이미 인증된 상태에서는
`/posts`로 이동한다. `/login?next=...`의 보호 화면 복귀 동작은 유지한다.

개발 서버의 `/auth-preview`에서 모의 계정(`student@syuin.ac.kr`, `admin@syuin.ac.kr`,
미인증 `unverified@syuin.ac.kr`, 비밀번호 `preview-password`)으로 로그인·권한·세션
만료·로그아웃 실패를 확인할 수 있다. `/signup-preview`에서는 인증번호 `123456`으로
가입 흐름과 입력 오류를 확인한다.
두 화면 모두 새로고침하면 초기화되며 운영 환경에서도 공개 데모로 열린다.

## 연결 방법

`authApi.ts`에서 세션 로그인·로그아웃·학교 이메일 가입을 처리한다.

- `me(): Promise<unknown>`: 현재 사용자 조회. 세션이 없으면 `null`을 반환하거나
  `ApiError(401)`을 그대로 던진다. 응답은 `toCurrentUser`가 id/displayName/role만
  남기며 형식이 다르면 로그인으로 취급하지 않는다.
- `login({ email, password })`: 세션이 발급된 경우에만 resolve한다. 실패는
  `ApiError`를 그대로 던지면 상태 코드별 안내(400·401 동일, 403 새로고침·이메일 인증
  상태 확인, 429 제한)를 표시한다. 403의 원인을 이메일 미인증으로 단정하지 않는다.
  성공 후 provider가 `me()`로 다시 확인한 뒤 진입한다.
- `logout()`: CSRF 헤더를 붙여 `POST /logout`을 호출한다. 서버는 302를 반환하며 브라우저는 리다이렉트를 따라가지 않는다.

회원가입은 `signupOperations`를 이용한다. 화면은 이메일 인증을 먼저 마친 뒤 가입을
요청한다. 백엔드 `main`의 `c55054f` 소스(2026-11-12 확인)는 이메일별 인증 상태를
30분 동안 보관하고 가입 시 소비한다. 세 요청 모두 CSRF 쿠키·헤더가 필요하다.

- `requestCode(email)`: 6자리 인증번호 발송. 등록된 이메일은 409, 재발송 제한은 429를 처리한다.
- `verifyCode(email, code)`: 성공 시에만 resolve. 400은 서버의
  `VERIFICATION_CODE_EXPIRED`·`VERIFICATION_CODE_MISMATCH`를 우선해 만료·불일치를
  안내하고, 위 두 오류 코드가 아니면 화면의 경과 시간으로 구분한다. 429는 실패 초과다.
- `register({ studentNo, name, schoolEmail, password })`: 이 네 필드만 전달한다.
  학번은 문자열로 유지하며 role·비밀번호 확인·동의 값은 요청에 포함하지 않는다.
  가입 인증이 만료되면 이메일을 다시 인증한다.

가입 인증번호는 발급 후 5분 동안 유효하다. 이미 가입한 이메일의 발송 요청은 409다. 학교 이메일 기본 허용 도메인은 syuin.ac.kr, syu.ac.kr이다.

루트 레이아웃의 `AuthProvider`가 앱 전체에 상태를 제공한다. 화면에서는
`useAuth()`로 `status`(`checking`·`authenticated`·`anonymous`·`expired`·`unavailable`)와
`user`를 읽는다. 보호 화면은 `<RequireAuth>`, 관리자 화면은 `<RequireAuth role="ADMIN">`로
감싼다. 다른 기능의 API가 401을 받으면 `handleUnauthorized()`를 호출하고, 403이면
`<AccessDenied />`를 표시한다. 이 가드는 화면 안내일 뿐이며 실제 권한 판정은 서버가 한다.

사용자가 바뀌거나 로그아웃·만료되면 provider 아래 트리를 다시 마운트하므로 이전
사용자의 화면 상태(명단·초안 등)가 남지 않는다. 화면 복귀(focus·visibilitychange)와
뒤로 가기 캐시 복원(pageshow)에서 `me()`를 다시 확인한다. 일시적인 재확인 실패는
로그인 상태를 유지하며, 보호 API의 401이 최종 판단이다.

## 성공·실패 처리

- 로그인: 이메일은 학교 도메인 두 개를 지원한다. 비밀번호는
  trim·정규화하지 않는다. 요청 중에는 중복 제출을 막고, 실패하면 비밀번호만 비운 뒤
  비밀번호 칸으로 포커스를 옮긴다. 서버 오류 원문은 표시하지 않는다.
- 회원가입: 이메일 인증 후 이메일을 고정하고, 바꾸려면 "다른 이메일로 변경"으로 인증을
  다시 시작한다. 재발송은 60초 간격(서버 429가 최종 판단), 인증번호는 숫자 6자리만 받는다.
  학번은 양끝 공백을 제거한 필수 문자열로 최대 20자, 이름은 NFC 후 양끝 공백을 제거해
  필수·최대 50자로 검사한다(길이는 UTF-16 코드 단위). 학번의 선행 0·내부 문자는 유지한다.
  비밀번호는 원문 8~64 UTF-16 코드 단위 및 UTF-8 72바이트 이하로 검사한다.
  필드 오류는 해당 칸을 고치면 사라진다. 실제 API 정책 차이는 위 연결 방법을 참고한다.
- 로그인 후 이동: `?next=`는 같은 출처의 `/` 경로만 허용하고 `//`, `\`, 제어 문자,
  `/login` 반복은 `/`로 바꾼다. 보호 화면의 로그인 링크는 현재 검색 조건도 유지한다.
- 로그아웃 서버 실패(네트워크·500): 이 기기의 사용자 정보는 지우고 실패를 안내하며
  "서버 로그아웃 다시 시도"를 제공한다. 이 동안 `me()`가 성공해도 자동으로 다시
  로그인하지 않는다(AC-AUTH-002-07).

- 이름 최대 50자·학번 최대 20자는 백엔드 `SchoolRegisterRequest` 제약을 따른다.
- 약관 "보기"는 전문이 없어 펼침 안내만 표시한다.
- 하단 "학교 계정 확인" 영역은 오류·안내가 있을 때만 표시한다.
- 회원가입 버튼 글자는 대비를 위해 `#477000`, 로그인 버튼 글자는 #9와 같은 `#212124`다.
- 로고는 Figma 원본 SVG(`public/auth/logo.svg`, 32×32)를 인증·서비스 공통 헤더에서
  재사용한다. 시안의 10px 간격과 워드마크 크기·자간을 적용했다.
- 계정 메뉴는 32px 이름 아바타와 16px 원본 펼침 SVG, 144px 흰색 메뉴 패널을 사용한다.
  계정명은 시안의 500 굵기를 적용하며 긴 이름은 줄이되 접근 가능한 전체 이름을 유지한다.
- 비밀번호 재설정 진입점은 시안에 없어 로그인 폼 아래에 추가했다(AC-AUTH-001-06).

## 비밀번호 재설정

`/forgot-password`에서 학교 이메일로 인증번호를 요청하고, 이메일·인증번호·새 비밀번호로 변경을 완료한다. `/reset-password`로 직접 들어와도 같은 폼을 사용할 수 있다. 인증번호·비밀번호는 URL이나 영구 저장소에 넣지 않는다. 60초 이내 재발송이나 미가입 이메일도 같은 안내를 받을 수 있다. 완료 후 새 비밀번호로 로그인한다. `/password-reset-preview`에서는 모의 응답으로 확인할 수 있다.

로그아웃 중 이전 조회 무시, 중복 제출·중복 로그아웃, 보호·관리자 화면 가드, 계정 메뉴의
Escape·바깥 클릭·포커스 복귀를 검증한다. 회원가입은 도메인, 동일 발송 안내, 재발송

약관 펼침을 검증한다.
